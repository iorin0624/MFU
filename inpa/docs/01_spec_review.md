# INPA V1 仕様レビュー

## 1. 結論

提示されたV1仕様は、独立サービスとして実装を開始できる水準です。特に、MFUとの
認証・DB分離、バックエンドでの公開制御、短い共有URL、モバイルファーストという
方針は整合しています。

実装前に解釈が分かれる点を本書で確定し、以下をV1の基準仕様とします。

## 2. 配置と独立性

アプリケーションに関係するファイルは、すべて次の配下へ集約します。

```text
/mnt/mfu/app/inpa
```

対象は、Vue、API、MFU管理接続層、マイグレーション、テスト、デプロイ設定原本、
運用スクリプト、文書です。

ただし、稼働中のsystemd unit、Webサーバーの有効化済み設定、Unix socket、journald、
MySQLデータファイルはOS・ミドルウェアの管理場所に存在します。これらの原本と再構築
手順を `inpa/deploy/` に置くことで、別サーバーへ移す際にINPAディレクトリを起点として
再構築できるようにします。

## 3. 矛盾・不足と確定方針

### 3.1 ルート直下の共有トークンとVueルートの競合

`https://inpa.mydns.jp/{token}` は短い一方、`/login` や `/settings` と競合する可能性が
あります。

確定方針：

- 固定ルートを先に判定します。
- 共有トークンはCrockford Base32の16文字とします。
- トークン用ルートは16文字の許可文字に一致した場合だけ処理します。
- `login` 等の予約語はトークンとして生成されません。
- DBにはSHA-256ハッシュを保存し、平文トークンは発行時以外保持しません。

16文字のCrockford Base32は80bitの探索空間を持ち、短さと推測耐性を両立します。

### 3.2 公開対象 `following` の向き

「自分が登録している人」は、予定所有者を基準に解釈します。

```text
予定所有者Aが閲覧者Bを登録している
A → B
```

この場合、BはAの `following` 向け予定を閲覧できます。閲覧者が所有者を登録している
だけの `B → A` は該当しません。

`mutual` は `A → B` と `B → A` の両方が存在する場合です。

### 3.3 公開対象ごとのアクセス経路

- `link`: 有効な共有URLを持つ匿名・ログイン済み閲覧者
- `logged_in`: 有効な共有URLまたは登録済み一覧から到達したログイン済み利用者
- `following`: 所有者が登録しているログイン済み利用者
- `mutual`: 所有者と相互登録になっているログイン済み利用者
- `private`: 所有者本人のみ

共有ページのAPIは、閲覧者の関係とトークンの有効性を毎回バックエンドで判定します。

### 3.4 予定の重複

V1では、1ユーザー・1シーズン・1日につき予定は1件とします。🏰TDLと🌍TDSを移動する
場合はパークを「両方」にします。この制約により月間人数と同日人数の二重計上を防ぎます。

### 3.5 日時の保存

- `visit_date` は日本時間の暦日を表す `DATE`
- `arrival_time` は日本時間を表す `TIME`
- 作成・更新・ログ日時はUTCの `DATETIME(6)`
- APIでは日時をISO 8601で返します

### 3.6 メモ・表示名・SNS名

すべてプレーンテキストとして扱い、HTMLは許可しません。Vueのエスケープに加え、
APIで長さ・制御文字・改行数を検証します。

V1上限：

- 表示名: 1〜40文字
- Xハンドル: 1〜15文字（先頭の `@` は保存時に除去）
- Instagramハンドル: 1〜30文字（先頭の `@` は保存時に除去）
- 仮装情報: 100文字
- メモ: 500文字

SNS名は本人確認済みとは表示せず、外部プロフィールへの自動リンクは安全なURL生成処理を
通します。

### 3.7 セッション有効期限

元仕様に期限がないため、V1では次とします。

- 通常ログイン: 最終利用から30日、発行から最長90日
- 「ログイン状態を保持しない」場合: ブラウザーセッション終了まで
- パスワード変更・退会・管理者失効時: 全セッションを直ちに失効
- セッション識別子はCookieのみ、DBにはハッシュだけを保存

### 3.8 メール送信

SPF・DKIM・DMARCは「可能であれば」ではなく、本番公開の前提条件とします。
`noreply@inpa.mydns.jp` を実際に送信元として利用できるか、DNSとメールサーバー設定を
公開前に検証します。メールは同期リクエスト内で直接送らず、DBキューを介してワーカーが
再送可能な形で配信します。送信待ちに必要な宛先とテンプレート値は環境変数の鍵で暗号化し、
送信完了または再送期限終了後に消去します。検索・集計用には宛先ハッシュだけを残します。

### 3.8.1 仮登録データ

最初のメールアドレス入力時点ではパスワードと表示名が存在しないため、未完成行を `users` に
作りません。`registration_requests` にメールアドレス、token hash、有効期限を保存し、確認リンク
からパスワードとプロフィールの登録が完了したトランザクション内で正式な `users` 行を作ります。
期限切れ・使用済みの仮登録は定期削除します。

### 3.9 Turnstile障害時

登録処理ではfail closedとし、検証できない場合は登録を受け付けません。既存利用者の
通常閲覧・ログインまで一律停止させません。不審ログイン時だけ追加チャレンジを要求します。

### 3.10 Rate Limit

複数workerで整合するサーバー側ストレージを使用します。V1では `inpa_db` の
`rate_limit_counters` を使用可能とし、負荷増加時にはINPA専用Redis/Valkeyへ差し替えられる
インターフェースにします。

IP単独の永久BANは行いません。IP、IPv6プレフィックス、メール、アカウント、端末Cookie、
操作種別を組み合わせ、一時制限とTurnstile再要求を基本にします。

### 3.11 ブロックと匿名閲覧

ログイン中のブロック対象者には予定を返しません。ただし、ログアウトして共有URLへアクセス
した人物を同一人物と断定できないため、匿名閲覧を完全には防げません。画面上でこの制約を
説明し、必要に応じて共有トークン再発行を案内します。

### 3.12 アカウント削除と保存期間

保存期間が未確定だったため、V1では以下を初期値とし、利用規約・プライバシーポリシーと
一致させます。

- 退会取消猶予: 30日
- 猶予中: ログイン不可、予定非公開、共有トークン無効、関係解除
- 猶予後: ユーザー識別情報と予定を完全削除または不可逆匿名化
- セキュリティイベント・管理監査ログ: 365日
- 通常アクセスログ: 90日
- メール送信ログ本文: 保存せず、宛先ハッシュ・種別・結果を180日

法的保全やインシデント対応が必要な記録は、理由と期限を監査ログへ残して別扱いにできます。

### 3.13 MFU Internal Admin APIの認証

同一サーバー上では外部TCPポートを開かず、Unix domain socketを使用します。

- socket所有グループだけ接続可能
- MFUからの要求に時刻・nonce・本文ハッシュを含むHMAC署名
- 60秒を超える要求とnonce再利用を拒否
- MFU adminのユーザー名を署名対象に含める
- INPA側で管理操作を必ず監査記録

別サーバー移設時は、同じAPI契約のままmTLS + HMACへ変更します。

### 3.14 MFU管理と完全分離の関係

MFUはINPA DBへ直接接続しません。`inpa/mfu_admin_bridge/` は表示とInternal Admin API呼び出し
だけを担当し、INPAの業務ロジックを持ちません。将来INPAを分離する場合、この薄い接続層だけを
MFU側に残せます。

## 4. V1で追加する必要がある非機能要件

- 対応ブラウザー: iOS Safari、Android Chromeの現行主要版を優先
- SNS内ブラウザー: X・Instagram・LINEで登録・閲覧を確認
- アクセシビリティ: キーボード操作、ラベル、色だけに依存しない状態表示
- API互換性: `/api/v1` と `/internal/admin/v1` を使用
- 可用性: メール障害が予定閲覧を停止させない
- バックアップ: 日次、暗号化、世代管理、定期復元試験
- ログ: 共有URLの平文トークン、パスワード、セッション、メール検証コードを記録しない
- 画像: V1では利用者画像アップロードを持たない
- キャッシュ: 権限付き予定APIは `private, no-store`
- 公開共有HTML: `X-Robots-Tag: noindex, nofollow` と `Referrer-Policy: no-referrer`

## 5. V1受入条件

1. 匿名利用者が有効な共有URLから許可された予定だけを閲覧できる。
2. 無効・再発行済みトークンでは予定を取得できない。
3. APIレスポンスに公開情報量を超えたフィールドが含まれない。
4. 利用者は自分の予定だけを追加・編集・削除できる。
5. 一方向・相互登録の公開判定が定義どおり動作する。
6. ブロック時に双方の登録が解除され、ログイン状態では相手の予定を取得できない。
7. メール未確認アカウントは主要機能を利用できない。
8. TurnstileとRate LimitをAPI側で回避できない。
9. MFUはInternal Admin API以外からINPAデータを操作できない。
10. すべての重要な管理操作がINPA監査ログに残る。
11. パスワード変更時に現在を含む全セッションが失効し、再ログインが必要になる。
12. メールアドレスは新アドレスの確認完了まで変更されず、完了後に全セッションが失効する。
13. 表示を許可していないSNS名は、本人以外へのAPIレスポンスにフィールド自体が含まれない。
14. 共有URLの同時再発行を行っても、1ユーザーに複数の有効tokenが作られない。
15. 退会猶予中にメールの取消tokenで復旧でき、失効済み共有URLは復活しない。
16. runtime用DBアカウントではDDLおよびMFU DBへのアクセスを実行できない。
