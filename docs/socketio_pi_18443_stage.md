# PiのNginx 18443番 HTTPS検証（2026-11-06）

## 結果

判定は**条件付き合格**。PiのApache 80/443番を維持したまま、ループバック18443番の独立Nginx → ループバック18091番のSSHトンネル → N5105の8091番へ、TLS・WebSocket・Polling・Redisイベント配信が通った。認証済みテストアカウントがないため、ログイン後のSocket.IO認証と各端末機能は未検証。公開443番の切替や高負荷試験は行っていない。

## 構成と実施内容

- PiにはDebian公式の `nginx` / `nginx-common` 1.22.1-9+deb12u10を導入。導入前に **nginx.serviceのみ** を永続マスクし、パッケージの自動起動を防いだ。既存Apacheは停止・再起動せず、80/443番を保持。Nginxの標準設定は起動せず、[独立した設定例](../deploy/socketio/nginx-pi-18443.conf.example)を `/etc/mfu/nginx-18443.conf` に配置し、構文検査後に手動起動した。
- Nginxは `127.0.0.1:18443` だけで待ち受け、既存のMFU証明書と秘密鍵を**元の場所から参照**した。通常HTTPはSNI・証明書検証付きでPiのApache `https://127.0.0.1:443` へ転送し、`/socket.io/` は `127.0.0.1:18091` に転送した。Nginxのアクセスログは無効、エラーログは検証専用。
- PiからN5105へ既存SSH鍵で `127.0.0.1:18091` → `127.0.0.1:8091` の短命トンネルを張った。新たな鍵や認証情報の恒久配置はしていない。作業端末からPiの18443番へも短命SSHトンネルを張り、**そのPythonプロセス内だけ** `mfu.iori0624.jp` を127.0.0.1へ解決させた。OSのhostsや通常ブラウザー設定は変更していない。
- 検証ブラウザーのOriginを受けるため、承認後に[一時環境変数例](../deploy/socketio/socketio-stage-18443.env.example)のとおり `https://mfu.iori0624.jp:18443` を8091番の許可リストへ追加し、**mfu-socketio-stageだけ**を再起動した。検証後は元のOrigin設定へ戻し、同サービスだけ再起動した。現在は18443番Originが再び400で拒否される。

## 検証後の状態と次の作業

検証用Nginxプロセス、Pi→N5105のSSHトンネル、作業端末→PiのSSHトンネルを停止し、18443/18091番が閉じたことを確認した。Nginxパッケージと設定ファイルは次回検証用に残し、**nginx.serviceはmasked/inactive**。Apacheの80/443番と本番8080番はそのまま稼働。8091番は元のOrigin設定で稼働し、自動起動は未有効。元設定の一時バックアップは復元確認後に削除した。

次は隔離したブラウザープロファイルと専用テストアカウントで、ログイン・Cookie・管理者/外部ユーザー/Windows端末の正常認証、ログアウト後の拒否、各名前空間のイベントを確認する。実際の8080番ワーカーからのテストイベント送信経路も未整備。これらを終えるまで公開443番の切替判定はしない。
